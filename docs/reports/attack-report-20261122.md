# 攻击面报告：一个「把文件放对位置」的下载器（2026-11-22）

> 问题起源：我们自己能想到的攻击只有"路径穿越"那一类。这份报告去查了案例与研究，
> 回答三个问题：**别人真被打过的是什么**、**我们挡不挡得住**、**哪些是我们结构上挡不住的**。
> 每一条都标了来源；没有来源的推断会明确写成推断。

## 0 一句话结论

**我们最大的风险不是路径穿越，而是"内容本身就是代码"**：整合包里的 `mods/*.jar` 就是可执行文件，
而我们（以及所有同类工具）交付的哈希**来自同一份被污染的清单**，它只能证明"传输没坏"，
证明不了"这东西不是别人放的"。路径安全（#9）挡的是"写到哪"，挡不住"写进去的是什么"。

## 1 口径与威胁模型

被测对象：`mc-downloader`（单次命令、跑完退出的 CLI，负责下载并按目录结构落盘/安装整合包）。

| 角色 | 能力 | 我们的假设 |
|---|---|---|
| 恶意源站 | 任意响应：200/206、畸形 header、无限体重定向、gzip | 用户自己选源（铁律 #1：不内置镜像、不自动换源） |
| 恶意整合包/清单 | 任意 `files[].path`、任意哈希、任意 `overrides/*` | **一定是不可信的** |
| 仿冒站点 | 诱导用户下载"启动器/整合包" | **我们管不到用户点哪里** |
| 本机其他进程 | 能在我们落盘窗口里改文件系统（软链竞态） | 不在当前威胁模型内 |

## 2 案例：这个生态真的被打过（按时间）

### 2.1 Fractureiser（2023-06，Minecraft 生态）

攻击者夺取了 CurseForge / BukkitDev 上项目的账号，把恶意代码塞进**看起来正常的 mod/插件 jar**，
其中一些被并入了**热门整合包**；CurseForge 报告约 6,500 次受感染文件下载。
来源：[fractureiser 调查报告](https://raw.githubusercontent.com/trigram-mrp/fractureiser/refs/heads/main/README.md)。

**对我们的意义**：这不是"用户从野站下了东西"，而是**官方平台自身的账号被夺**。
"从官方源下载"并不构成充分防御。

### 2.2 假 mod 通过 GitHub 账号网络传播（2025-06，Check Point）

"Stargazers Ghost Network" 用一批看起来正常的 GitHub 账号分发伪装成 Minecraft 作弊/辅助 mod 的 jar
（`Oringo`、`Polar`、`Taunahi`、`FunnyMap` 等），估计 **1,500+ 台设备**受影响。
报告特别指出：**恶意 Java 下载器在 VirusTotal 上全引擎不报**，因为沙箱里没有它需要的依赖，跑不起来。
来源：[Check Point Research](https://research.checkpoint.com/2025/minecraft-mod-malware-stargazers/)。

**对我们的意义**：① 用户拿到的 jar 来自"看起来像开发者"的账号；② **杀软/沙箱对这类样本经常无效**，
所以"我扫过毒"不是判据。

### 2.3 WeedHack（2026-01 起，产业化）

一个在 `weedhack.to` 上的**犯罪平台**：客户可以生成针对 MC 1.21.0–1.21.11 的定制载荷，
甚至**把恶意代码注入合法 mod**；通过 SEO 投毒 + YouTube 引流，已识别 **3,820 个恶意 jar、240+ 个传播 URL**，
用 EtherHiding（以太坊合约当死信箱）拿 C2。
来源：[EnigmaSoft 汇总](https://www.enigmasoftware.com/zh-hans/weedhackmalwarecampaign-removal/)。

**对我们的意义**：注入合法 mod 之后再算哈希，哈希也是"对的"——**哈希证明不了来源**。

### 2.4 HMCL 仿冒站（2026-07，瑞星）——离我们最近的一条

钓鱼站点 `hmcl.io` 冒充 HMCL 启动器官网，投递 `hmcl.zip`（21.6 MB，MD5 `3DF90F27485B785DE9731D09240CA2D7`）：
里面是**白加黑**——带 Microsoft 有效签名的 `HMCL-3.13.2.exe` + 同目录恶意 `dsetup.dll`（DLL 侧加载），
随后静默安装 ScreenConnect 远控、注册 LSA 身份认证包做持久化。
来源：[瑞星博客](https://rayblog.rising.com.cn/2026/07/%e4%b8%8b%e8%bd%bd%e6%b8%b8%e6%88%8f%e5%90%af%e5%8a%a8%e5%99%a8%e5%8d%b4%e8%a3%85%e4%ba%86%e4%b8%aa%e8%bf%9c%e6%8e%a7%ef%bc%9fhmcl%e4%bb%bf%e5%86%92%e7%bd%91%e7%ab%99%e6%ad%a3%e5%9c%a8%e5%88%a9/)。
来源给的细节值得记：**合法签名 + DLL 侧加载**意味着"看数字签名"这条常识也会失效。

### 2.5 Rust 生态的 zip-slip 是**正在发生**的漏洞类

RustSec 的 `zip-slip` 关键词下同时挂着六条（2026 年内）：
`RUSTSEC-2026-0297`（unzip）、`-0307`（uncbv）、`-0328`（decompress，tar 系）、`-0427`（sn-releases）、
`-0434`（ant-releases）、`-0503`（eazip，**symlink 目标校验传错了参数**，Windows 上可越界）。
来源：[rustsec.org/keywords/zip-slip](https://rustsec.org/keywords/zip-slip.html)。

**对我们的意义**：① 我们 #9 修的正是这一类，不是假想；② `eazip` 那条说明**软链目标校验**是独立的一类
（我们承认的 TOCTOU 残留与之同族）；③ 我们自己用的 `zip` **9.8.1** 不在这些通告里，但这不构成"以后也不会"。

### 2.6 协议级：`Content-Length` 整数截断 → 请求走私（CVE-2026-57488）

超过 32 位的 `Content-Length` 在某些实现里被截断成小数，导致收发双方对"body 有多长"理解不一致
（经典 request smuggling）。
来源：[CVE-2026-57488 分析](https://cve.imfht.com/intel/854172?lang=en)。

**对我们**：我们是**客户端**，不转发请求，所以走私打不到我们；但"对长度的理解不一致"这条同样适用（见 §3.3）。

## 3 逐条判定：我们的现状

### 3.1 内容级（结构性，挡不住）

| 攻击面 | 现状 | 判据 |
|---|---|---|
| **mod jar 就是代码** | **挡不住**：我们只负责放到 `mods/`，用户下次启动游戏就会执行 | 这是产品定位，不是缺陷；能做的只有**不自动运行**（我们确实不运行）与文档警告 |
| **哈希自证** | `.mrpack` 的 `sha1` 与 `downloads` 出自同一份 `modrinth.index.json`；CurseForge 的 `sha1` 也来自同一次 API 响应 | ⇒ 哈希只能证明**传输完整**，不能证明**来源可信**。任何人能改清单就能同时改哈希 |
| **`fetch` / `generic` 无 `--sha1`** | 当前**默认接受**；`--require-sha1` 可拒绝（见 §5 第 4 项） | 用户从野站下东西时，等于"任意内容直接落盘"。要挡得加 `--require-sha1` 之类的显式开关（**未实现**，记入待办） |
| **杀软/沙箱** | **不能当 gate**。本机实测（2026-11-22）：`root\SecurityCenter2` 只登记了 Windows Defender，而 Defender 的 `AMServiceEnabled` / `RealTimeProtectionEnabled` / `AntivirusEnabled` 三项全是 `False`；真正在跑的**火绒 6.0.0.1** 不在 SecurityCenter2 里。火绒官方只给 `HipsMain.exe -s "<路径>"`（仅自定义查杀；且明确"不支持打印安全日志的参数、指令"） | 见 §2.2（这类样本在 VT 上常常全绿）与 `docs/reports/platform-abilities-20261123.md` §A：**能把扫描拉起来给人看，不能当 gate**；输出里不许出现"已扫描 / 通过 / 安全" |

> 本节只给攻击面判定；"本机/两平台上有什么可调、值不值得用"的完整清单（火绒 / Windows / Linux / HTTP）
> 见 [`platform-abilities-20261123.md`](platform-abilities-20261123.md)，那里每条都带判据与代价。

### 3.2 路径级（已修）

| 攻击面 | 现状 |
|---|---|
| URL 末段 / 清单 `files[].path` / zip 条目名的 `..`、绝对路径、盘符 | **已修**（#9，`src/pathsafe.rs`，五个接缝 + 集成测试） |
| Windows 专属：ADS、保留名、尾部点空格 | **已修**（仅 Windows 生效） |
| 软链目标（`eazip` 那类） | **部分**：已存在的软链会被 `canonicalize` 前缀比对挡住；**校验到落盘之间的竞态**（TOCTOU）挡不住，见决策记录 Consequences |

### 3.3 协议级（部分修，部分未测）

实测（本机 2026-11-22，四种畸形 `Content-Length`，敌意服务器）：

| 情形 | 结果 |
|---|---|
| `Content-Length: -1` | 下载中断（响亮失败），无成品 |
| `Content-Length: 9999999999999999999999`（超 u64） | 同上 |
| `Content-Length: 1099511627776`（1 TiB，能装进 u64） | 同上；回退到单流后留下 4096 B 的 `.part`（下次会因"有 `.part` 无 `.state`"从头下） |
| 重复且冲突的 `Content-Length: 100` / `200` | 同上 |

**归因限制（别当成结论）**：这四条都是"下载中断"，但**没能区分是 hyper 在解析层拒了、还是我们
`header_content_length` 里 `parse::<u64>().ok()` 归一化成 `None` 之后走了单流**。要分开它们需要在
桩服务器上做 206 响应（不能像这次这样让服务器忽略 Range，否则会先触发 #6 的回退路径）。

其余未测项（按价值排序）：**重定向换对象**（302 后拿到另一个文件 → 现在只有 #7A 的总长比对能抓）、
**`Content-Encoding: gzip` 强压**（`reqwest` 未启 gzip feature ⇒ 压缩字节会被当正文写入，`fetch` 无 sha1 时静默坏文件）、
**`429/503` 的归因**（分片路径现在把所有非 206/200/416 都报成「服务器不支持 Range」，`download.rs:907`；
`Retry-After` 在下载路径也没读，退避是纯 `1 << attempt` ⇒ 排查会被引向相反方向）、
slowloris、TLS 自签、恶意代理改写响应。其中 `429/503` 这条的判据与代价见
[`platform-abilities-20261123.md`](platform-abilities-20261123.md) §D；前两条见本报告 §5。

### 3.4 来源级（代码挡不住，只能靠产品约束与文档）

| 攻击面 | 现状 |
|---|---|
| 仿冒站点诱导下载（§2.4） | 挡不住；我们不做官网推荐、也不自动换源（铁律 #1 顺带限制了这条） |
| 镜像投毒 | 挡不住；`probe` 只测速不选源、不内置镜像 —— 这是**定位**层的防御，不是技术防御 |
| CurseForge API key 泄露 | 挡不住；文档写明需要用户自备 key |

## 4 我们明确挡不住什么（写清楚，免得以后误以为挡了）

1. **恶意 jar 的内容**：我们不反编译、不扫签名、不跑沙箱。这是刻意的（§2.2 已说明扫了也常无效）。
2. **清单自证的哈希**：改清单的人能同时改 URL 与哈希。
3. **用户点进仿冒站**：`hmcl.io` 这种域名，代码层无从判断。
4. **运行期**：我们只落盘，不启动游戏；落盘之后的执行不归我们管。

## 5 下一步可执行清单

| # | 实验 | 判据 | 状态（2026-11-23） |
|---|---|---|---|
| 1 | 重定向到**另一个对象**（先 302，再 206 不同长度） | 必须报「远端文件大小变了」，不能拼出跨对象文件 | **单跳 302 已实测**：跟随重定向，落盘内容 = 目标对象（4096 B），无跨对象拼接。**落地名取原始 URL 末段**（`/redirect` 而不是 `b.bin`）——这是 `filename_from_url` 的既定语义，不是 bug。**下载中途换对象**仍未测（要 206→302→不同长度） |
| 2 | 强制 `Content-Encoding: gzip` | 要么拒，要么明确写明"不透明字节"；`fetch` 无 sha1 时不许静默成功 | **已修**：现在直接拒绝（见 §3.4），实测未落盘 |
| 3 | 206 桩 + 四种畸形 `Content-Length` | 分离"hyper 拒绝"与"我们的 `None` 归一化" | 部分已覆盖：`Fault::TruncateMid` 测"声明整片、只发一半"⇒ 分片长度校验命中（`buf.len() != expect`）。**四种畸形 `Content-Length` 那组还没重跑** |
| 4 | `fetch` 增加 `--require-sha1` 或至少对"无校验和"打一行显式警告 | 用户下野站文件时不能静默 | **已做**：`--require-sha1`（默认关），实测拒绝并给出出路 |
| 5 | slowloris（慢 header / 慢 body） | `read_timeout` 生效，且错误信息说清是"读超时"不是"服务器不支持" | **实测：`read_timeout` 无法阻止"慢滴"**。服务器每 0.5s 吐 1 字节、`--timeout 2` 下，进程**挂了 7 分钟以上仍未退出**（本次探测是被手工杀掉的）。原因：`read_timeout` 是"单次读不返回"的超时，每 0.5s 都返回 1 字节 ⇒ 永不触发。**这是已知缺口**，修法见下 |

### 5.1 slowloris 的修法（未实现）

不能退回 `ClientBuilder::timeout`（那会把大文件的合法长传输也掐死，见 §3 的取舍）。
正确做法是**停滞检测**：在写入循环里记录"最近 N 秒内是否推进了至少 M 字节"，
低于阈值就主动中断并报「服务器传输停滞」。代价是要在 `one_stream` 与 `fetch_piece` 两个循环里
各加一份状态；判据是"慢滴服务器在 2×N 秒内失败，且正常慢链路（1 MB/s）不受影响"。

## 7 限制

1. §2 的案例都有"平台自述"的成分（CurseForge 的 6,500 是**下载次数**，不是感染数）；这类数字只能当量级看。
2. §3.3 的探测只覆盖四种畸形值，而且**归因未分离**（见上）。
3. 这份报告没有做"我们的用户实际被打了多少次"的统计——我们没有遥测，也不该有。
4. 检索是 2026-11-22 一次快照；这类事件更新很快，引用前请重新核对。
