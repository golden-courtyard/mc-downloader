# 版本号与标签

这份文档规定：**什么时候跳版本、跳哪一位、标签长什么样**。目的只有一个 —— 让人看到 `0.6.0`
就知道它相对 `0.5.0` 是什么性质的变化，而不是靠猜。

## 一、先把历史事实说清（"跳得随意"的来源）

| 版本 | 时间 | 出现在哪个提交 |
|---|---|---|
| `0.1.0` | 2026-10-21 | `b525541` 初版（vanilla + pack） |
| `0.5.0` | 2026-10-21 | `5f08c68` 工程配置收口 + 清 dead code |
| `0.6.0` | 2026-11-23 | 源自备 + 文档体系那一批 |

**`0.2` / `0.3` / `0.4` 从来没有存在过** —— 从 `0.1.0` 一步跳到 `0.5.0`；而且在此之前**没有任何 tag**，
所以"0.5.0 里到底有什么"只能翻提交记录猜。这就是"随意"的具体形态：**不是数字大，是没有规则**。

**这次不改历史**：首个公开版本仍叫 `0.6.0`。数字回退（改成 `0.1.0`）会让全部提交、CHANGELOG 与文档里
所有 `0.6.0` 引用对不上，而它并没有错，只是没规则。**从这一版起有规则**，就够。

## 二、标签形态（只借 dsh 的**命名**，不借它的编号）

```
mc-v0.6.0            # 正式版
mc-v0.7.0-alpha.1    # 预发布：alpha.N → rc.N → 正式
mc-v0.7.0-rc.2
```

- **名字**：`<包简写>-v<semver>`；本仓库简写取 `mc`（与 dsh 的 `dsh-v…` 同形）。
- **类型**：**轻量标签**（`git tag mc-v0.6.0`，不带 `-a`）。dsh 的 44 个 tag 都是 `commit` 类型。
- **一致性**：标签里的版本号**必须**等于 `Cargo.toml` 的 `version`。
- **每个 tag 对应一个 `release(mc): x.y.z` 提交**：该提交只做三件事 —— 改 `Cargo.toml`、刷新 `Cargo.lock`、
  把 CHANGELOG 的 `[Unreleased]` 收成版本节；**正文列出本次包含的决策记录**（见 §四）。

> 诚实说明：dsh 的 tag 数量多、alpha 与 rc 交替，**它自己的编号也看不出稳定规则**（也出现过对外跳号）。
> 所以这里只照它的**形态**（前缀、轻量、预发布后缀），编号规则由本文定义。

## 三、跳哪一位（0.x 阶段）

| 变化 | 跳哪 | 例 |
|---|---|---|
| **破坏性**：用户必须改配置或改脚本 | **minor** | 0.6.0（`[source]` 六项变必填、脚本要 `schema`） |
| **只加可选功能**，不动既有用法 | **minor** | 0.7.0 |
| **只修 bug** | **patch** | 0.6.1 |
| 预发布 | **挂在"目标版本"后面** | `0.7.0-alpha.1` … `0.7.0-rc.1` → `0.7.0` |

三条硬规矩：

1. **不许跳号**。下一个 minor 就是当前 +1（`0.6` → `0.7`）。两次破坏性变更落在同一个 minor 里，
   不拆成 `0.8`、不"凑个整齐的数"。
2. **预发布属于某个目标版本，不是独立的变化类型**。先定目标（`0.7.0` 还是 `0.6.1`），再排 `alpha`/`rc`。
3. **patch 原则上不发预发布**。唯一正当理由是"这个修复本身有风险，先小范围试"——
   写了这条就不是禁止，而是**要求说出理由**。

**alpha 与 rc 的区别**（否则两个后缀没有意义）：

| 阶段 | 允许什么 | 不允许什么 |
|---|---|---|
| `-alpha.N` | 契约仍可调整（配置键、脚本字段、CLI 语义） | 不能声称兼容 |
| `-rc.N` | **只接受修复**；契约冻结 | 任何破坏性改动 —— 有就回 `alpha` |

## 四、跳哪一位由**决策记录**推导（不是拍脑袋）

自上个 tag 以来，看 `.agents/notes` 里新增或变更的条目，按下面这张表定版本：

| notes 里发生了什么 | 版本 |
|---|---|
| 有 `implemented/{architecture,feature}` 且改了**契约**（配置键 / 脚本 schema / CLI 语义 / 落盘布局） | **minor** |
| 有 `implemented/feature` 但只新增可选能力，不动既有契约 | **minor**（0.x 阶段合并，见 §三） |
| 只有 `implemented/bug-fix` | **patch** |
| 只有 `proposed`（还没实现） | **不发版** |
| 有 `rejected` / `archived`，且它**撤回了已发布过的契约** | **minor**（本质是破坏性） |

于是 `release(mc): x.y.z` 提交的正文必须能回答"为什么是这一位"，写法就三行：

```
release(mc): 0.7.0

包含的决策记录：
- implemented/feature/2026-11-23-xxx.md（改 `[source]` 语义 ⇒ 破坏性）
- implemented/bug-fix/2026-11-24-yyy.md
```

**为什么绑到 notes 上**：这个仓库的决策记录本来就是"为什么这样"的唯一住所（`AGENTS.md` §六）。
版本号如果能把"这一版包含哪些决策"直接映射出来，就不需要另写一份 release notes 解释自己；
反过来，一个版本若既找不到对应的 note、又说不清为什么跳位，那它大概**不该发**。

## 五、什么时候才配 1.0

四条同时满足才行，缺一条就继续 0.x：

- [ ] **配置与脚本格式稳定**：连续两个 minor 没有破坏性变更（`[source]`、`schema = 1` 这类契约不再动）；
- [ ] **关键路径有真机验证记录**：原版 / Fabric / Forge / NeoForge 各自的"装完能启动"都有人验过；
- [ ] **已知缺口都处理或明确不修**：issue 里没有"我们知道但不打算修"的隐身项；
- [ ] **有人依赖它**：至少一个外部使用者在真实场景用过一个版本周期。

## 六、发布流程里对应哪几步

见 [release.md](release.md)。与本文件相关的三步：

1. CHANGELOG 的 `[Unreleased]` → `[x.y.z] - YYYY-MM-DD`（只改标题，内容不洗）；
2. `Cargo.toml` 改 `version`、`cargo build` 刷新 `Cargo.lock`（diff 应只有本包那一行）；
3. `git tag mc-vx.y.z && git push origin mc-vx.y.z`，**tag 与 `Cargo.toml` 必须一致**。

> 首个标签 `mc-v0.6.0` 指向 `0579556`（提交信息是 `docs: 版本号与标签规则…`，因为它同时冻结了 CHANGELOG）。
> 从 `0.7.0` 起严格执行 §二：**tag 只打在 `release(mc): x.y.z` 那个提交上**。
