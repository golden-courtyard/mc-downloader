# 测试设施：现在有什么，云服务器 / Kali / Docker 各自能买什么

回答一个具体问题：「租一些 Windows 和 Linux 云服务器，再配 Kali，能多做哪些测试？Docker 用现成的镜像吗」。

先说结论：**能买到的最大价值不是"更多机器"，而是"更多网络条件"与"真机装配验证"** ——
而这两件事里只有一半能自动化。下面按"值不值"排序。

## 一、现在的三层设施

| 层 | 在哪 | 能测 | 不能测 |
|---|---|---|---|
| 单元 / 参数化 / 属性 | `cargo test`（186 + 40） | 已知失败模式 | 任何真实网络行为 |
| 假服务器 | `tests/http_semantics.rs` 的 `Fault` 变体 | 截断、谎报长度、416、Range 回 200、慢滴 | TLS、CDN、代理、真实 RTT |
| 本机定量 | `scripts/quant/` + `docs/reports/` | 默认值合不合理（并发、分片、超时） | 跨地域、跨运营商 |

## 二、Kali（已有）：测"网络病理"，不可 CI 化

它是**中间人**，价值在三件事：

1. **netem**：丢包、RTT、抖动、乱序 —— 用来校准 `StallGuard` 窗口与 `--timeout` 的默认值；
2. **RST / 半关闭 / 慢滴**：这些是我们修过 bug 的地方（见 `docs/reports/net_faults-report-20261021.md`）；
3. **可控源**：同一份文件走 Range 与不走 Range、带 ETag 与不带，用来验证 `--if-range` 与降级路径。

限制：Kali VM 在桥接校园网，**IP 会飘**；它是单机，不能代表跨地域。所以它的定位是"发现未知失败模式"，
不是"日常回归" —— 这也是为什么每发现一条都要在单测里补最小复现（`AGENTS.md` 的硬性要求）。

### 2.1 一个必须说清楚的事：我们用的**不是** Kali 特有能力

回头看实验里真正调用过的东西：`tc qdisc … netem`、`curl`、
Python 的 `ThreadingHTTPServer`、`ssh`。这些**全是 mainline Linux 能力**（`iproute2` + 标准库），
Debian / Ubuntu 装两个包就有，与发行版无关。

| 能力 | 是不是 Kali 特有 | 我们用了吗 |
|---|---|---|
| `tc netem`（丢包 / RTT / 限速 / 乱序） | 不是，`iproute2` 自带 | **用了**（定量报告里的 400 mbit / 8 mbit 档） |
| 假源（Python / `nginx`） | 不是 | **用了** |
| `mitmproxy` / `bettercap`（TLS 中间人、协议改写） | **是**，Kali 的强项 | **没用**：我们只走 HTTP，不需要解 TLS |
| `nmap`（端口 / 服务识别） | 是 | 没用：目标地址是已知的 |
| `tcpdump` / Wireshark | 不是（但 Kali 预装好用） | 没用：靠日志与 `tc` 统计就够了 |
| 无线 / 密码审计工具 | 是 | 完全无关 |

所以 Kali 在这个项目里的真实角色是：**一台已经装好并接通的 Linux 小机**（sshd、
python3、iproute2 都在，而且 MCP 通道已经配好），不是“因为它叫 Kali”。

对测试策略的含义：

- **不要把“Kali”写成前提**。需要的只是“一台可以 `tc` 的 Linux”。
- **要 CI 化的那部分就不该用 VM**：`toxiproxy` / `nginx` 在 Docker 里跑得更快也更可重复。
- **Kali 的真正优势是一次性探针 + 图形化手工分析**（例如用 Wireshark 看一次异常握手）。
  那种场景确实比一个空白容器省事；但它不是我们**已经用上**的能力。

## 三、云服务器：值不值，取决于你想回答哪个问题

| 想回答的问题 | 需要什么 | 值不值 |
|---|---|---|
| 「源速受地域影响多大？」`SourcePool` 的 EWMA 参数是不是地域特异 | 2–3 个地域的小机器（按小时计费） | **值**：这是当前唯一没法在本机测的东西，且直接影响 `--piece-conns` 默认值 |
| 「Linux 上真能装完并启动吗？」 | Linux 机器 + 一个启动器 + 显示环境 | **部分值**：能验证"装完目录对"，但"进游戏"要 GPU/显示，云上做不了，别自欺 |
| 「Windows Server 上 MotW / 权限有问题吗？」 | Windows 云主机 | **低**：MotW 是客户端下载语义，Server 与桌面版的差异不在我们这条路径上 |
| 「跨运营商（电信/联通/移动）差异」 | 三家各一台 | **低**：这类差异由用户的实际网络决定，我们改不了，只能靠 `probe` 让用户自己选 |

**成本纪律**：按小时开、跑完就关；每次实验前先把口径写下来（`AGENTS.md` 的三条规矩），
否则会重复"跨时刻比较造出不存在的 22 倍回归"那种错误（`.shared/postmortem/0044`）。

## 四、Docker：用现成镜像，但别用错镜像

**要用的**（都是通用服务器，可控性优先）：

- `nginx` / `httpd`：造"支持/不支持 Range""带/不带 ETag""强/弱压缩"的源 —— 配置比写 Python 桩更接近真实；
- `squid` / `tinyproxy`：造代理异常（407、CONNECT 被拒、半关闭），验证 `--proxy` 路径；
- `toxiproxy`：注入延迟/带宽/断开，比 netem 更好 CI 化（它是应用层代理，能在 CI 里跑）。

**不要用的**：`itzg/minecraft-server` 这类 **MC 服务端**镜像。它测的是"服务端能不能起来"，
与我们的装配路径无关；而"装完能不能进游戏"需要客户端 + 显示，自动化收益极低。
用它只会得到一个跑得很慢、却什么都没证明的 job。

**最该做的一件事**：把 `Fault` 假服务器搬进 Docker（或直接做成 `tests/` 里的 `toxiproxy` 用例），
让"网络病理"第一次进 CI —— 现在这些用例只能在本机手工跑，回归全靠人记得。

## 五、建议的实施顺序

1. **Docker 化假源 + toxiproxy 用例进 CI**（收益最高，成本最低，纯自动化）；
2. **Kali 补一轮 netem 扫描**，把 `StallGuard` 窗口与 `--timeout` 的默认值定下来，写进定量报告；
3. **按小时租 2–3 台不同地域的小机器**，只回答"源速/分片默认值是否地域特异"这一个问题；
4. 真机装配验证（Windows 桌面 + Linux 桌面）留到发布前，人工按 README 走一遍 —— 云服务器替代不了它。

## 六、这些都不做的代价

说清楚不做的后果，免得看起来像"以后再说"：

- 不做第 1 项：网络病理回归只能靠人记得 → 已经发生过"修好的 bug 半年后换个形状回来"；
- 不做第 2 项：`StallGuard` 的窗口只能是拍的值（现在 `max(10s, 2×timeout)` 有实测支撑，但只在本机）；
- 不做第 3 项：`--piece-conns 4` 的"最优"只在本机网络上成立，跨地域可能不成立；
- 不做第 4 项：发布说明里的"实测"就只能引用旧记录。
