# 平台范围：Windows 是产品，Linux 是回归，macOS 没进过决策

这份文档回答一个被问过的问题：「为什么从没考虑过 macOS」。

**诚实版本**：不是权衡之后否掉的，是**从来没进过决策**。没有人为它提过需求，
也没有一份文档写过"不做 macOS"。这一篇就是把那个空位补上，把话说明白。

## 一、现在的三段事实

| 平台 | 状态 | 判据 |
|---|---|---|
| **Windows** | **产品**。唯一做了真机验证的平台 | README 的验证状态表：PCL 实机进游戏（Forge / Fabric）、NeoForge 真机 `EXIT=0` |
| **Linux** | **回归**，不是产品 | CI 的 `check` job（ubuntu-latest）跑 fmt / clippy / test / release build。**没有**真机装配验证 |
| **macOS** | **不在支持范围** | 没有 CI job、没有真机验证、没有 issue 模板里的选项 |

## 二、为什么 macOS 排到最后

三条按重要性排：

1. **用户在哪**。这个工具的落脚点是"给 PCL / HMCL 这类启动器准备好目录"。这两个启动器的主战场是 Windows；
   macOS 上的等价物是官方启动器或第三方启动器，社区规模小一个量级。**为不存在的用户做兼容，是纯负债。**
2. **我们真正差异化的两处能力是 Windows 专属的**：Mark-of-the-Web（`src/motw.rs`，写 `Zone.Identifier`
   备用数据流）在 macOS 上没有对应概念；盘符与大小写不敏感路径规则（`pathsafe`）也是 Windows 语义。
   把这两块按平台拆开，收益是"能编译"，成本是**每个分支都要多一套测试**。
3. **没有验证能力就不该声称支持**。我们没有 macOS 机器，也没有人愿意长期在 macOS 上手工跑
   "装完能不能启动"这一步。**"能编译"和"能用"是两件事**，README 的验证状态表就是为了不让这两件事混起来。

## 三、代码层面 macOS 会怎样

`cargo build` 大概率能过：`#[cfg(windows)]` 之外没有平台专属系统调用，
依赖（reqwest / tokio / zip / sha1）都是跨平台的。但**这是推断，不是实测** ——
没在 macOS 上跑过一次，就不要在文档里写"支持"。

真要声称支持，最低门槛是：

- [ ] CI 加 `macos-latest` job（fmt / clippy / test / build）
- [ ] `tests/linux_semantics.rs` 那类平台断言扩一份 macOS 分支（大小写、路径分隔符、`/tmp` 语义）
- [ ] 有人在真机上按 README 的「五分钟上手」装一次原版 + Fabric，并**实际启动成功**
- [ ] README 的验证状态表加一行，写明"谁在什么机器上验的"

## 四、如果以后要做，顺序是什么

1. 先有需求（issue 里出现真实的 macOS 用户，而不是"顺手支持一下"）；
2. 再上 CI job（这一步只是证明"能编译能测"）；
3. 最后才是真机验证 —— 没有第 3 步，前两步只能换来一句"未验证"。

**在此之前**：macOS 相关的 issue 按 `enhancement` 处理，不承诺时间；
文档里不要出现"支持 macOS"的字样，也不要为了让它编译通过而加没有测试覆盖的 `cfg(macos)` 分支。
