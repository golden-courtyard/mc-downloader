# Agent Note: 分片下载必须校验 Content-Range 起点

Status: implemented

## Problem

`fetch_piece` 原来只校验两件事：`status == 206`、`buf.len() == expect`。

**这两条抓不到"起点错"**：服务器返回 206、`Content-Length` 也对，但 `Content-Range`
的起点不是请求的位置（CDN 缓存错位 / 多源镜像配错 / 代理改写 Range 头），
长度检查会通过，随后 `f.seek(pj.start)` + `write_all` 把数据写到**错误的偏移**上。

后果的形态特别难查：

- 不报错 —— 每一步都"成功"
- 文件大小正确 —— 每个分片都写满了自己的长度
- 只有整文件 sha1 错 —— 而且重试多半还是错的（同一个坏源，同一个坏缓存）

对照：IDM 每段开工前都比对起点，它的调试日志原文是
`Start data for this chunk is matched with start of the file`。

## Decision

1. **分片级校验区间，不只看长度**：`Content-Range: bytes <s>-<e>/<total>` 的 `<s>`
   必须等于请求起点、`<e>` 必须等于请求终点（闭区间）。
2. **区间换算收成单点**：`byte_range(start, end_excl) -> (start, end_excl - 1)`。
   请求头（`Range: bytes=<s>-<e>`）与校验实参**共用同一次换算** ——
   两处各写 `pj.end - 1` 时，任一侧单独漂移都会让**所有**分片被判"区间不符"，
   而纯字符串单测全绿、看不出来。单点化后由 `byte_range` 的单测锁住。
3. **单位大小写不敏感**：`BYTES` / `Bytes` / `bytes` 都接受（ABNF 字面量本就如此）。
   为了一个大小写把本来能用的服务器判死，方向反了 —— 这条校验的目的是"抓真正的错位"，
   不是"当格式警察"。
4. **格式非法一律响亮失败**：缺单位、缺 `/`、缺 `-`、数字解析失败 ⇒ `Err`，不 panic。
5. **`total` 只校验格式，不比对实际文件大小**：`*`（未知）跳过；比对交给全文件 sha1。
   要在这里比就得把 `file_size` 传进 `fetch_piece`（改签名），收益不抵成本。
6. **206 但不带 `Content-Range` ⇒ 硬失败**，不降级为 warn。

## Alternatives considered

| 方案 | 为什么不做 |
|---|---|
| **保持现状（只校验长度）** | 就是本文 Problem 那条：静默拼出 sha1 错的文件。**响亮失败比静默错文件便宜** —— 前者一次重试/换源就恢复，后者要人肉二分定位 |
| **降级为 warn，继续写盘** | **这是最坏的一档**：日志里一行 warn 没人看，出来一个"大小对、sha1 错"的文件，比直接失败贵得多。**校验的价值就在于"不过就不写"** |
| **用 `If-Range` / `ETag` 根治"同偏移不同文件版本"** | 真正的根治手段：带上版本标识，不一致就让服务器回 200 全量。但**要求所有镜像共享同一套 ETag**，现实里多镜像/多 CDN 各自算 ETag，条件必然失败 ⇒ **会把"能用但慢"的镜像直接判死** |
| **宽进：接受 `bytes=100-199/1000`（等号分隔）** | RFC 7233 的格式是 `bytes <s>-<e>/<total>`，等号**非法**。大小写宽容是因为 RFC 说它合法；等号宽容是**我们自己发明一套容错语法**，维护成本大于收益 —— 真遇到这种服务器，报错让人知道"这源不守规矩"比悄悄迁就更有用 |
| **拿 `Content-Length` 交叉验算区间长度** | `buf.len() == expect` 已经在做同一件事（且更直接，量的是真实字节数）。再加一条是重复 |
| **在 `one_stream`（不分片路径）也校验** | 那条路径没有 `Range` 请求，`Content-Range` 本来就不该出现；整文件 sha1 是它的完整性保证 |

## Consequences

**变好的**：

- 起点错位从"静默坏文件"变成**可读的响亮失败**，错误消息同时带
  「服务器回的区间」「请求的区间」「原始 header」三项 —— 一眼能判是不是 CDN/代理的问题。
- 三条失败出口（缺头 / 非 ASCII / 区间不符）口径统一：都先 `record_failure` 再报错。
- `pj.end - 1` 只有一处定义，漂移面被单测锁住。
- **416 现在会说出远端当前多大**（2026-11-23 补）：416 的 `Content-Range: bytes */N`
  就是"远端现在是 N 字节"（RFC 9110 §14.4）。以前只报"可能已变小或被替换"，用户还得自己 HEAD 一次；
  现在错误里直接写「远端当前 N 字节，我们按 M 字节在切」。只认 `*` 形式 ——
  `bytes 0-99/N` 出现在 416 里是服务器不规范，按"没给"处理而不是瞎猜。

**代价 / 已知残留**：

- **行为变更面**：以前"206 但不带 `Content-Range`"的畸形服务器能下成功，现在硬失败。
  这类服务器不合 RFC 7233（206 必须带 `Content-Range`），判死是**有意的**；
  但确实存在"以前能过、现在过不了"的源。
- **`total` 只校验格式、不比对文件大小**：这条取舍**已被重新提起**（issue #7 的方案 A：把
  `Content-Range` 的总长与 `job.size` 比对，让"远端对象中途被换"报精确错误）。
  本文保留原判据（要在这里比就得改 `fetch_piece` 签名）；改判要等 #7 的结论，别两边同时改。
- **`record_failure` 不再"空写"**（2026-11-22 更正）：原记录说源不会变，是因为当时只有
  `one_split` 建 job 时调一次 `pick()`。现在 `one_split` 每个分片带 `tried: Vec<usize>`，
  重试会换源、无源可换时抛 `SourcesExhausted` —— `record_failure` / `record_success`
  喂的 EWMA 与 `fail_streak` **是有消费者的**。原结论作废，改由
  `source.rs` 的注释与 `one_split` 的重试环承重。
- **`206 缺 Content-Range` 这个分支仍零覆盖**：三行 `ok_or_else`，写错概率低；
  要覆盖得搭 HTTP 桩 —— 桩现在有了（`tests/http_semantics.rs` 的 `FaultServer`），
  补一条就是十几行的事，见 #2 收尾时留下的清单。
- **`pj.end == 0` 会 `end - 1` underflow panic**：本次未引入新风险
  （`Range` 请求头早就在做这个减法），且切片保证 `end > start`。记录在案，不在本次范围。
