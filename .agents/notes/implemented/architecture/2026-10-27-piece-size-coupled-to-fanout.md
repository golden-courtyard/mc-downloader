# Agent Note: 片大小应与并发数耦合，而不是先按文件大小切死

Status: implemented

## Problem

`download.rs:440` 一行决定了实际连接数：

```rust
let conns = opts.piece_conns.min(n_pieces).max(1);
```

**`n_pieces` 由 `PieceTable::new` 按文件大小算死**（`piece.rs`）：

| 常量 | 值 | 含义 |
|---|---|---|
| `NO_SPLIT_BELOW` | 8 MB | 低于此不分片（1 片）|
| `PIECE_MID` | **4 MB** | 8 MB–256 MB 每片 4 MB |
| `LARGE_ABOVE` | 256 MB | 超过此每片 **16 MB**（片更大 ⇒ 片更少）|
| `PIECE_LARGE` | **16 MB** | — |

**⇒ 推演（配置 `piece_conns = 4` / `= 32` 两种情况）**：

| 文件大小 | 片大小 | 片数 | 实际连接（配置 4）| **实际连接（配置 32）** |
|---|---|---|---|---|
| 9.28 MB | 4 MB | 3 | 3 | **3**（片数不够）|
| 100 MB | 4 MB | 25 | 4 | 25 |
| **256 MB** | **16 MB** | **16** | 4 | **16**（**配 32 也没用**）|
| 1 GB | 16 MB | 64 | 4 | 32 |

**⇒ 两个反直觉处**：
1. **文件越大，片越大** ⇒ **片数增长得比文件慢** ⇒ 256 MB 时配 32 也只有 16 连接
2. **`piece_conns` 调高在中等文件上完全无效**（被 `min` 吃掉）

**⇒ 用户实测感受的正是这个**：「IDM 能把 32 线程拉满，我们只能四个」——
**不是"我们只支持 4"，是"片数先锁死了上限"**。

## Decision

**把因果反过来**：**先由并发数决定片大小**，而不是"先切片、再看片数够不够"。

```
piece_size = clamp(size / conns, MIN_PIECE, MAX_PIECE)
  MIN_PIECE = 1 MB      // 防碎片化：片太小会让每连接的重建开销占比过高
  MAX_PIECE = 16 MB     // 与现在的 PIECE_LARGE 对齐，保持大文件行为不变
```

**规则**：
- **`size < NO_SPLIT_BELOW`（8 MB）** ⇒ 仍不分片（单流）—— 小文件分片无收益
- **`size ≥ 8 MB`** ⇒ `piece_size = clamp(size / target_conns, 1 MB, 16 MB)`

**⇒ 效果**：
- **100 MB + 32 连接** ⇒ 片 = 3.1 MB ⇒ **33 片** ⇒ **32 连接跑满**
- **256 MB + 32 连接** ⇒ 片 = 8 MB ⇒ **32 片** ⇒ **32 连接跑满**
- **1 GB + 32 连接** ⇒ 片 = 32 MB → 被 clamp 到 16 MB ⇒ 64 片 ⇒ 32 连接

**当时还打算把 `adaptive` 的默认值从 `false` 改为 `true`** —— **这一半没有采纳**（2026-11-22 判定）：
`../../../docs/reports/quant-report-20261122.md` 的 E1 显示带宽受限链路上 1→64 连接的吞吐差只有 3%（44.8 vs 43.5 MB/s，
issue #4 §二 的判据要求 A ≥ 1.2×B 才值得做自适应），而 E2 显示机械盘上连接越多墙钟越慢（2.06×）。
⇒ 再加一层控制环没有依据，默认值保持 `false`；`--adaptive` 保留为手动开关。

## Alternatives considered

| 方案 | 为什么放弃 |
|---|---|
| **只把 `piece_conns` 调高**（不改切片逻辑）| **实测推演无效**：256 MB 文件配 32 也只有 16 连接（片数不够）。**这是本次要解决的核心问题** |
| **一律切小片**（如固定 1 MB）| **小文件反而更慢**：9.28 MB 会变成 10 片但每片只有 1 MB，**连接建立开销（TCP+TLS 握手）摊不平**；且**片太小会让 `.part.state` 的元数据占比上升** |
| **抓包逆向 IDM 的二进制** | **不需要，而且方向错**。见下节——**分段策略写在 HTTP 请求里，不在代码里** |
| **直接抄 IDM 的 32 连接默认值** | **默认值应与"典型文件大小"匹配**。本项目主要下 MC 文件（100 KB–30 MB 的库、几十 MB 的 client jar），**这些文件根本用不上 32 连接**；默认 4 是合理的，**问题在"调高无效"**，不在"默认值小" |

### 关于「逆向 IDM」这件事（写清边界，避免以后重复讨论）

**结论：不需要逆向，抓包就够；而且抓包看到的是「实际行为」，比代码里的「设计意图」更可信。**

| 想知道 | 抓包 | 逆向 |
|---|---|---|
| 初始发几个 Range | 直接看请求头 | 要追算法 |
| Range 边界多大 | 可以 | 同 |
| **中途有没有动态加段** | 看新请求出现时机 | 看不到"实际跑了几个" |
| 并发数怎么变 | 数在飞的连接 | 要追状态机 |

**具体做法**（抓的是本机流量，合法）：

```
① 找一个 100 MB+ 的静态直链（不要网盘，要支持 Range）
② 用 IDM 下，同时用 mitmproxy / Wireshark 抓 HTTP
③ 记三个数：初始 Range 个数、Range 大小、中途新增 Range 的时刻与大小
```

**法律边界**（也写在这里，免得下次又议一遍）：

- **抓自己机器的流量** —— 合法
- **读公开文档 / 界面提示** —— 合法
- 注意：**反编译二进制** —— EULA 明确禁止（合同违约），不必然违法，但**没有必要性**
- **破解授权验证** —— **违法**（《计算机软件保护条例》第 24 条：故意避开技术措施）
- **抄代码** —— 侵犯著作权

## Consequences

**已落地**（`PieceTable::with_conns`，2026-10-27；2026-11-22 起再向下取整到 4 KiB，
见 [piece-page-alignment](2026-11-22-piece-page-alignment.md)）：片大小由 `size / target_conns` 算出、
夹逼在 `[MIN_PIECE, MAX_PIECE]`，片数不再成为并发的隐性天花板。

**当时的验收条与今天的状态**（2026-11-22 逐条核过 —— 别让读者以为都做到了）：

| 当时写的验收条 | 今天 | 说明 |
|---|---|---|
| 1. `piece_size = clamp(size / target_conns, 1 MiB, 16 MiB)` | **成立** | 另加页对齐（见上） |
| 2. `size < NO_SPLIT_BELOW` 仍不分片 | **成立** | 单流路径 |
| 3. 实际并发 = `min(配置, 片数)` 且 `片数 ≥ 配置` | **成立** | 由 `piece_count_meets_conn_target` 看着 |
| 4. `adaptive` 默认改 `true` | **未采纳** | E1：带宽受限链路上 1→64 连接的吞吐只差 3%（判据要求 ≥1.2× 才值得做自适应）；E2：机械盘上连接越多墙钟越慢（2.06×）。见 `../../../docs/reports/quant-report-20261122.md` |
| 5. `cargo test --lib` 全绿 | **成立** | 当时 113 条，现 138 条（含 5 条页对齐用例） |
| 6. 真机对比测速（100 MB 直链，conns=32） | **未按原样做** | 被 2026-11-22 的定量分析取代：E1 给出环路峰值在 conns=4、右尾下降；E2 给出机械盘墙钟惩罚。结论比原计划更细，但**没有**这一条端到端对比 |

**当时的风险与缓解，事后回顾**：

| 当时担心 | 结果 |
|---|---|
| 触碰引擎核心（改错会静默下坏文件） | 改动只落在切片计算，`.part.state` 格式没动。后续反而在这里发现一个**既有**缺陷（续传按 conns=4 重建判据），见页对齐 note |
| 片太小导致握手开销 | 有实证支持：E1 里 conns=64 那档片最小、吞吐最低（245 MB/s） |
| 服务端限流 / 封 IP | 默认仍 4；`piece_conns` 是用户配置，文档写明调高可能被限流 |
| 多文件并发 × 分片并发 = 爆炸 | `split_for()` 仍按文件数均分，本轮未改动 |
| "并发高 ≠ 更快" | **被 2026-11-22 的数据完整证实**，而且比预期更糟：机械盘上并发越高越慢（见 #8）|

**仍然成立的教训**：用户感受到的"IDM 能拉满 32"确实来自"片数先锁死上限"，这个诊断是对的；
但**拉满 32 ≠ 更快** —— 后续数据说明真正的瓶颈常在链路与写路径，不在连接数。
