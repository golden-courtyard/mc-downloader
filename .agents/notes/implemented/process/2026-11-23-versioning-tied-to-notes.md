# Agent Note: 版本号由决策记录推导

Status: implemented

## Problem

`0.1.0` 一步跳到 `0.5.0`（`0.2`–`0.4` 从未存在），而且首个 tag 直到 `0.6.0` 才打。
于是"`0.5.0` 里有什么"只能翻提交记录猜。用户的原话是"版本号跳得有些随意了感觉"。

更具体地问：**"只修 bug → patch" 与 "预发布迭代 → `-alpha.N`/`-rc.N`" 是冲突的** ——
表里没说预发布挂在哪个目标版本上，也没说 patch 要不要预发布。规则有洞，等于没规则。

另外，拿 dsh 当参照时发现：它的 44 个 tag 形态统一（`dsh-v0.2.3-alpha.2`、轻量标签），
但**编号本身也看不出稳定规律**（alpha 与 rc 交错，也出现过对外跳号）。所以"照 dsh 做"不能代替规则。

## Decision

**两件事分开：形态照 dsh，编号自己定。**

1. **形态**：`mc-v<semver>`、**轻量标签**、`-alpha.N` / `-rc.N` 后缀、每个 tag 对应一个
   `release(mc): x.y.z` 提交。
2. **编号规则**（补掉那个洞）：
   - 预发布**不是独立的变化类型**，它挂在**先定好的目标版本**后面（先决定是 `0.7.0` 还是 `0.6.1`）；
   - **patch 原则上不发预发布**，唯一正当理由是"修复本身有风险，先小范围试"；
   - `-alpha` 允许改契约，`-rc` 只接受修复（契约冻结，有破坏性改动就回 alpha）；
   - **不许跳号**：下一个 minor 永远是当前 +1，多次破坏性变更落在同一个 minor 里。
3. **版本由 notes（决策记录）推导**：自上个 tag 以来，
   - 有 `implemented/{architecture,feature}` 且改了契约（配置键 / 脚本 schema / CLI 语义 / 落盘布局） ⇒ **minor**；
   - 只有 `implemented/bug-fix` ⇒ **patch**；
   - 只有 `proposed` ⇒ **不发版**；
   - `rejected`/`archived` 撤回了已发布契约 ⇒ **minor**。
   并且 `release(mc)` 提交的正文必须列出本次包含的 note 路径 —— 让"为什么跳这一位"可查。

## Alternatives considered

- **回退成 `0.1.0` 再公开发布**：否。189 条提交、CHANGELOG 与文档里所有 `0.6.0` 引用都要改，
  而历史数字本身没错，错的是没有规则。回退只是把"随意"换成"抹掉"。
- **完全照 dsh 的 tag 序列**：否。它的形态值得借，但它的编号看不出规则（见上），照抄等于把随意制度化。
- **用日期版本（`2026.11.23`）**：否。0.x 阶段最需要表达的是"破坏性 vs 修复"，日期版做不到；
  而且 `Cargo.toml` 的 semver 字段与它天然冲突。
- **只按"变更类型"定版本、不管 notes**：否。那样又回到拍脑袋 —— 没人能复核"这次算不算破坏性"。
  绑到 notes 上，任何一次跳位都能追到具体文档。
- **让 CI 强制 tag 与 `Cargo.toml` 一致**：本轮未做（tag 触发需要单独的 workflow）。
  目前靠 `release.md` 的清单 + `release(mc)` 提交模板。

## 定量核对（2026-11-23 补）

对参照项目 44 个 `dsh-v*` 标签做了定量观察（脚本 `scripts/quant/versioning_vs_notes.py`，
报告 `docs/reports/versioning-vs-notes-20261123.md`）。三条与我们这条决策直接相关的发现：

1. **每次发布带走的是 `implemented` 新增**（中位 33 份/发布），而 `proposed → implemented` 的迁移
   很少在一个发布窗口内闭合（中位 0、均值 0.3）。⇒ 本文"按 `implemented` 推导版本位"的选择有实证支持；
   `proposed` 会跨多个发布累积，不该拿它当"没进展"的证据。
2. **`-rc` 段不是"只修 bug"**：rc 与 alpha 的 note 构成几乎相同（feature 24.8% vs 24.7%），只是批量更小。
   ⇒ `versioning.md` 里"rc 冻结契约"这条**改标为我们的自有纪律**，不再以参照项目为依据。
3. **时间序上出现过核心版本回退**（2 次，`0.1.7-alpha.1` → `0.1.5-rc.3` 等）。
   ⇒ 新增一条"版本不许回退"的硬规矩；机器判据（对比上一个 `mc-v*` 标签）本轮未实现，已记在报告 §六。

## Consequences

**变好的**：

- `0.6 → 0.7` 这种位移有据可查：跳位依据是 notes 的类别，不是"感觉这次改动大"；
- 预发布有明确归属，patch 发预发布需要理由，"只修 bug / 预发布迭代"不再冲突；
- 首个 tag 形态与 dsh 一致（`mc-v0.6.0`，轻量），以后再公开也不显得异类。

**代价 / 已知残留**：

- **首个标签没走完整流程**：`mc-v0.6.0` 指向 `0579556`（提交信息是 `docs: …`，因为那次提交同时冻结了
  CHANGELOG）。从 `0.7.0` 起严格执行"tag 只打在 `release(mc)` 提交上"。
- **没有机器判据**：tag 与 `Cargo.toml` 是否一致、`release` 正文是否列了 notes，目前都靠人。
  要固化需要"tag 触发的 workflow"，本轮没做（记在 `docs/dev/release.md` 的待办里）。
- **notes 的 class 命名成了契约的一部分**：以后若改 `.agents/notes` 的目录结构，
  这张推导表要同步改，否则规则会指向不存在的路径。
