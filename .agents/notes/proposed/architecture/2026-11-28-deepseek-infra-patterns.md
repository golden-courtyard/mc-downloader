# Agent Note: 从 DeepSeek 基础设施仓借三个模式（慢源回归 · 任务级续跑 · 小文件批量）

Status: proposed — 三条各自独立、可分别落地；判据先测现状再定阈值。证据来源标在每条内文，未实测的一律注明

## Problem

`deepseek-ai` 的仓在 2026-11 集中活跃，其中 `3FS`、`DeepEP`、`smallpond`、`DeepInfer` 与「搬数据」这件事有关。
问题是：**哪些设计模式对我们的下载器真的有用，哪些只是别人的物理条件**。不写下来，下一轮又会从头翻一遍，
而且容易把营销说法当成结论。

本记录只收**能在我们代码里指出对应位置**的模式；主观上是"借形态不借实现"。

参考的形态（读的是 README 与目录结构，**没有读它们的实现代码**）：

| 仓 | 读到的东西 | 性质 |
|---|---|---|
| `DeepEP` | 高吞吐 kernel 与低延迟 kernel 两套路径，统一在同一个 `EPBuffer` 接口下；SM/QP 数量可配 | README 明写 |
| `3FS` | 分离式架构；强调大规模并行 checkpoint | README 关键词 |
| `smallpond` | DuckDB + 3FS 之上的轻量数据框架，分区级任务 | README（2.2 KB，未细读实现） |

## Proposal

### 一、慢源的 half-open 回归探测

**对应形态**：DeepEP 的低延迟路径刻意不占 SM（避开"慢的那一半"），3FS 同样回避慢盘。

**我们现状**：`src/source.rs` 已有 EWMA 吞吐（`ewma_bps`）与失败计数（`fail_streak`），`pick_excluding` 按吞吐排序。
缺的是**熔断后的回归判定**：现在一次成功就把 `fail_streak` 清零，源刚恢复又挂时会在"恢复 → 秒挂 → 再熔断"之间抖动。

**提议**：熔断的源不删除、按指数退避放行单个探测请求；探测成功才恢复参与分配，失败继续退避。
形态等价于熔断器的 half-open 状态。

### 二、任务级续跑（在分片级之上加一层）

**对应形态**：3FS 的并行 checkpoint 与 smallpond 的分区级重试，都是"以任务为单位记进度"，而不是只记字节。

**我们现状**：`PieceState`（`.part.state`）已经是**分片级** checkpoint —— 单个文件中断可续。
批量场景（脚本里多个 `[[task]]`）中断后重跑，仍要重新扫目录、重新判断哪些文件已存在。

**提议**：批量执行时维护一份**任务级 resume 记录**（每个 task 的完成标记与产物校验和），
重跑时先读它，跳过已完成的任务；与 `.part.state` 互补，不替代。

### 三、小文件批量模式

**对应形态**：DeepEP 两套 kernel 按负载切换（训练 prefill 追吞吐、解码追延迟），统一在一个接口下。

**我们现状**：`one_split` 与 `one_stream` 按"服务器是否支持 Range + 文件大小"分流，这对大文件是对的；
但对**成千上万个 1 KiB 小文件**，每个文件的建连 + TLS + HEAD 固定开销占比会压过传输本身。

**提议**：加一条"小文件批量"路径：不切片、高并发、连接复用、元数据合并请求。
判据不是"更快"，而是"固定开销占端到端时间的比例降到多少"。

## 明确不借（同属证据）

1. **RDMA / 零拷贝 / 集群元数据服务**（3FS）：我们是单机客户端、公网 HTTP，没有这些物理条件。
2. **GPU 校验**：下载器的瓶颈在公网带宽（并发峰值 4，源端从 2257 塌到 468 MB/s，见定量报告）；
   校验再快也不改变总时长。GPU 在"元素级并行"任务上有效（bootstrap 实测 5–158×），但那是另一类问题。
3. **"0.01 秒剔除坏节点、无缝切流"**：这是某篇推文对 `mirrors.cernet.edu.cn` 的说法，
   实测该站只做 302 跳转（`curl -I` 得 `302 Found`），客户端不会自动重试；不采信，也不写进判据。

## Alternatives considered

- **不写，保持口头讨论**：下一轮重新调研 same set of repos，成本比写这份高。
- **直接抄实现**：它们的实现建立在 RDMA/NVLink/集群元数据服务上，物理条件不同；抄来的是复杂度。
- **四条一起做**：三条互不依赖，一起做会把"哪条有用"混在一起，无法归因。
- **把 GPU 校验也算进来**：见下节明确不借；我们已有实测（bootstrap 上 GPU 5–158×，下载器上无用），
  结论是"看瓶颈位置"而不是"用 GPU"。

## 其他候选（读过，暂不立项）

这三个形态有价值，但**要么前提不成立，要么收益未测**，先记下来，不混进上面的三条。

### 四、冗余副本 + 均衡装箱（EPLB）

`EPLB` 的做法：把负载高的专家**复制**成冗余副本，再用 `balanced_packing`（按权重降序贪心装箱）把副本铺到各卡上，
并尽量把同组专家放在同一节点以减少跨节点流量。源码 `eplb.py`，75 行左右，算法可读。

对应到我们：热点分片可以在多个源上冗余，并按"源"打包分配以减少建连抖振。

**为什么暂不立项**：EPLB 的权重是**离线已知**的（按历史负载算），我们的源吞吐是**在线未知**的（EWMA 边测边用）。
把离线装箱搬到在线场景，等价于假设带宽稳定——而我们的实测恰恰显示源端会从 2257 塌到 468 MB/s。
要立项，先回答"权重怎么在线更新、更新频率多高"，这是另一个实验。

### 五、有界重放 / 有界校验（DeepInfer 的 bounded replay）

`DeepInfer` 的 decoder 只重放"有界的后缀"（覆盖 SWA 窗口 + 最大回退长度），而不是从头重算。

对应到我们：续传时可只校验**有界的尾部窗口**，而不是全文件重扫。

**为什么暂不立项**：这会把"完整性"从"全文件校验"降级为"局部校验"，漏检概率要单独测。
在拿到漏检率之前，它是一条**降低保证**的改动，与铁律 5（校验失败必须重下）冲突，须先证伪风险。

### 六、调度与传输重叠（DualPipe / DeepInfer 的异步调度）

`DualPipe` 让计算与通信互相填满；`DeepInfer` 把 CPU 批调度与设备执行重叠。

对应到我们：**在传输当前分片时预取下一任务的元数据**、**把校验与写盘重叠**。

**为什么暂不立项**：需要先测"元数据阶段占总时长多少"。若占比本来就小（小文件批量除外），
重叠的收益就落在噪声里。这一条应该和第二条（小文件批量）一起测，不单独做。

## Acceptance criteria

三条各自可以独立验收，**阈值先测现状再定**，不在本记录里拍数字：

1. **half-open**：用 toxiproxy 注入"间歇性失败 → 恢复"的源，统计同一源在 5 分钟内
   "失败→恢复→再失败"的抖动次数；要求相对现状下降 ≥50%，且稳态吞吐损失 ≤2%。
2. **任务级续跑**：批量任务中断后重跑，记录"目录扫描与存在性判断"耗时占端到端时间的比例；
   要求降到 5% 以下，且不得因 resume 记录损坏而漏下文件（损坏时必须退化为全量扫描）。
3. **小文件批量**：构造 1000 个 1 KiB 文件的任务，测固定开销占比与端到端时间；
   与现有 `one_stream` 路径对照，要求在吞吐不下降的前提下降低固定开销占比。

## Risks

- **交互复杂**：half-open 与现有 `AdaptiveGate`（并发窗口）可能互相干扰，需要明确"谁在什么时候生效"。
- **状态文件腐蚀**：任务级 resume 引入新的状态文件，损坏时会漏下 → 必须能退化为全量扫描（已写进判据）。
- **小文件模式的选择依据**：按"大小 + 数量"还是按"探测到的 RTT"分流，选错会让大文件走进小文件路径。
- **样本内偏差**：以上判据都依赖我们自己构造的场景（toxiproxy / 1000 个小文件），外推到真实来源时要重测。
