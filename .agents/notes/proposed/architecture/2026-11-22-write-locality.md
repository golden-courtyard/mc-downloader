# Agent Note: 写局部性比页对齐更重要（乱序写 · NTFS VDL · 预分配）

Status: proposed — 数据已支持立项（E2 写放大 1.345–1.718×、机械盘墙钟 1.60–2.06×；E6 已证伪"预分配"）。方向与验收见内文，跟踪 issue #8

## Problem

分片下载器把「并发」用在网络上，却把「写盘」做成了**乱序**：每片下完就地 `seek + write_all`，
片的完成顺序由网络决定，与文件内偏移无关。4 KiB 对齐（见
[piece-page-alignment](../../implemented/architecture/2026-11-22-piece-page-alignment.md)）解决的是
页/扇区粒度的小事，**解决不了这件事**：

1. **HDD 的跳变代价是常数级**：每次跳变要付一次寻道 + 旋转（USB 外接盘还要加 USB 往返）。
   随机写代价 ≈ 跳变次数 × `t_hop`，而乱序时跳变次数 ≈ `B / piece_size`。
2. **NTFS 的有效数据长度（VDL）**：`SetFileValidData` 的文档明确说该函数能「避免在非排队写入时
   使用零填充」——反过来说，**默认路径会零填充** `[VDL, 写偏移)` 那段。先写高位片就可能触发
   一次大范围零填充（文档级推断，需 E2 的「物理写入字节 / 文件大小」证实）。
3. **预分配方式**：我们用 `set_len`（稀疏），等价于 aria2 的 `trunc` —— 而 aria2 的
   `--file-allocation` **默认是 `prealloc`**（非稀疏），官方手册在 ext4/xfs/NTFS 上推荐 `falloc`。
   多连接乱序写的碎片是它的已知问题。

### 模型（可算、可被推翻）

```
T ≈ B/BW + H · t_hop
  H     = 写跳变次数（相邻两次写的偏移不连续即计 1；由 strace/ETW 提，不靠猜）
  t_hop = 每次跳变的代价 —— **由数据拟合**，不是常数假设
⇒ 乱序时 H ≈ B/p，寻道开销占比 = t_hop·BW/p
⇒ 令它 < 10%：p_min ≈ 10 · t_hop · BW
```

`p_min` 与现有的 `MIN_PIECE = 1 MiB` 是否冲突，**取决于拟合出的 `t_hop`**：这是本提案唯一的
量化判据，也是它必须先测量的原因。

### 旁证：3FS 的选择（DeepSeek 的 Fire-Flyer File System，[design notes](https://github.com/deepseek-ai/3FS/blob/main/docs/design_notes.md)）

它解决的是「上千块 NVMe + RDMA」的问题，不能照搬，但有三条选择与我们的处境同构：

1. **文件切成等长 chunk，chunk 号由 inode + 索引直接算出**，读写不必每次问元数据服务 ——
   对应我们的「片的区间由 `PieceTable` 现算、进度旁挂在 `.part.state`」。这条我们已经在做，无需改。
2. **写是串行化的**：原文是「All writes are serialized at the head target」，并且一个 chunk 的更新
   是「把 committed 版本读进内存、应用更新、写成 pending 版本」——**整块读-改-写**。
   这给 A2 候选①一个直接先例：**并发放在网络上，串行放在写盘上**；也说明「对齐到 chunk 粒度」
   （MB 级）在存储系统里是常态，4 KiB 只是它的最细情形。
3. **批量提交**：USRBIO 的 `Iov`/`Ior` 是「大块共享内存 + 按 `io_depth` 成批提交」，
   动机是消掉小请求的 RPC 开销 —— 对应我们的「整片缓冲、一次写完」；反过来说，
   **小文件路径（< 8 MiB 不分片）现在是按流式 chunk 多次小写**，那一段没有批量。

**不适用的部分**（写清边界，免以后重复讨论）：CRAQ 副本链、FoundationDB 元数据、RDMA 零拷贝、
200 路 striping、无本地缓存/直写 —— 都是为「上千 SSD + 网络」服务的；单机 + HDD + 页缓存
没有这些问题。3FS 自己也指出「样本通常不是 4K 对齐」只是**小随机读**的痛点，
而我们是大块写 —— 这也解释了为什么 4 KiB 对齐对我们的收益有限。

## Proposal

**先做候选 ①：按片序重排写缓冲。** 网络侧并发一点不动（E1 显示并发对吞吐仍有正收益），
只在**写入端**把完成顺序重排回片序：维护一个以片号为键的窗口，落盘线程只写"当前最小未写片"，
超过窗口的完成片先攥在内存里、并阻塞取片。

它消掉的正是根因：E6 已经反证"放大来自乱序写触发的 VDL 零填充"，而 ① 让写偏移单调递增，
顺带把机械盘的跳变次数从 `H ≈ B/p` 压到 ≈ 1。

### 候选与代价（① 为本提案方向，②③④ 为备选）

| 候选 | 做法 | 代价 | 若采纳的验收 |
|---|---|---|---|
| ① 按片序重排缓冲 | 网络并发不变，写入端按片序落盘（窗口 × 片大小封顶内存） | 内存上限要设计；落盘线程成为单点 | 写跳变次数 H 降到 ≈ 1；端到端耗时下降且不劣化小文件路径 |
| ② 非稀疏预分配 | Windows：先顺序写一遍零；Linux：`fallocate`（要安全封装的新依赖，仓里 `unsafe_code = "forbid"`） | Windows 多一次顺序写（≈ 文件大小 / 顺序写速）；Linux 加依赖 | **E6 已证伪**：1 GiB 在 D: 上预分配 36.7 s + 下载 20.7 s = 端到端 57.5 s > 不预分配 44.0 s。它确实把写放大从 1.718 压到 1.02，但**多付一遍完整顺序写**，远超「额外耗时 < 5%」的判据 |
| ③ 写背压 | 以 `Avg. Disk sec/Write` 为反馈降写速率（应用层闭环，与内核 `blk-wbt` 不打架） | 要新增反馈通路与参数 | 磁盘拐点出现时端到端耗时下降；不引入吞吐回退 |
| ④ 每片临时文件 + 顺序合并 | 每片写自己的文件，全部到齐后顺序拼成目标文件（IDM 一类下载器的做法；3FS 也提到 FUSE 上「并发写同一文件」受限，应用改用多文件） | 峰值磁盘占用最多翻倍；多一次合并读写（全顺序，但确实 2× 写） | 合并阶段是纯顺序；`|Δoffset|` 的跳变在合并阶段 ≈ 0；总耗时与①比较 |

## Alternatives considered

| 方案 | 为什么不选 |
|---|---|
| **预分配（写一遍零 / `fallocate`）** | **E6 已证伪**：1 GiB 在 D: 上预分配 36.7 s + 下载 20.7 s = 端到端 57.5 s > 不预分配 44.0 s。它确实把写放大从 1.718 压到 1.02，但**多付一遍完整顺序写**，远超「额外耗时 < 5%」的判据 |
| **只把 `--piece-conns` 默认值调低 / 按介质分档** | 回避而不是修：E1 显示并发对吞吐有真实收益（环路 4 连接比 1 高 42%），牺牲它换写局部性不划算；分档还要先廉价识别介质，跨平台不可靠 |
| **维持现状**（把 1.6–2.06× 当"机械盘固有代价"） | 默认值在机械盘上就吃掉 60% 墙钟（E2），这是**默认值的错**，不是用户的错；而且根因（乱序写）是可修的 |
| **`SetFileValidData`** | 需要 `SE_MANAGE_VOLUME_NAME` 特权，且文件不能是稀疏。**这是唯一"不写零就能把 VDL 推到末尾"的路**，将来若重提预分配，只有这条有意义 |
| **`O_DIRECT` / `FILE_FLAG_NO_BUFFERING`** | `tokio::File` 不支持，且要自管页对齐内存；对齐只解决扇区与页共享，解决不了乱序 |

## Acceptance criteria

**决策层（已满足，2026-11-22）**：E2 写放大 1.345–1.718×、机械盘墙钟 1.60–2.06× ⇒ 两条判据都命中；
E6 证伪了"预分配"这条替代方案。故本 note 保持 proposed，等实现。

**实现层（立项后按此验收）**：

1. D: 上 1 GiB、`--piece-conns 16`：**写跳变次数 `H` 从 62 降到 ≈ 1**（strace 可数）。
2. 同一条件端到端 **≤ `--piece-conns 1` 的 1.1×**（E2 基线 21.4 s），且 `WA_raw` ≤ 1.1。
3. **小文件路径零变化**：`< 8 MiB` 走 `one_stream`，不改写路径、不新增内存峰值。
4. **内存有硬顶**：窗口 × 片大小 ≤ 64 MiB（或同等明确上限），超限必须**阻塞取片**而不是丢数据。
5. **续传语义不变**：`.part.state` 格式不动；中断后能续（含非默认 `--piece-conns`）。

## Risks

| 风险 | 说明 | 缓解 |
|---|---|---|
| 触引擎核心 | ① 要动 `one_split` 的写入路径（AGENTS 标记的 ★ 文件） | 先出数据与设计，改的时候单测覆盖片序与续传 |
| 结论只管这台机器 | `D:` 是 USB 外置 HDD（512e、4 KiB 簇）；目标是 NVMe 时 `t_hop` 小到可忽略 | 报告写明适用范围；默认值是否按介质分档，由数据决定 |
| `H` 借用平台 | 完成顺序在 Linux 侧测（strace），Windows 只测 T 与写放大 | 报告标注该假设，并用两种 `--piece-conns` 交叉检查 |
| 写锁成为新单点 | 按片序落盘意味着写入端串行（一把锁 + 一个「最小未写片」游标） | 每片一次 14–16 MiB 的 `write_all`；顺序写在这块 USB HDD 上实测 47.9 MB/s（E2 的 conns=1 就是顺序写），已接近网络侧。若真成瓶颈，再考虑双缓冲或按批提交 |
| 预分配的代价被低估 | 写一遍零本身是顺序写，在 HDD 上也许反而更慢 | E6 直接测「额外耗时」，不猜（结果：更慢，已证伪）|
