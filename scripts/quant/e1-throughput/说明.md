# e1-throughput：并发与吞吐

这是"三分离"（数据 / 口径 / 运算）在 `scripts/quant` 里的第一个落地样例。约定本身见
[`scripts/quant/README.md`](../../README.md)。

## 怎么跑

```bash
python scripts/quant/e1-throughput/standardize.py     # raw → out/tidy.csv（只做换算与标记）
Rscript scripts/quant/e1-throughput/calc.R "$PWD"     # tidy + config → result.txt（判据 PASS/FAIL）
```

两个脚本各自独立：`standardize.py` 不含统计，`calc.R` 不含数据与阈值。

## 目录各是什么

| 文件 | 角色 | 改它意味着 |
|---|---|---|
| `data.json` | 数据真源（实验问题、测量日期、raw 指针） | 换了一次新的测量 |
| `config.json` | 口径与判据（单位、剔除规则、阈值） | 改了判定标准 —— **必须在本文"阈值变更"里写为什么** |
| `standardize.py` | 标准化：raw → tidy，含**单位自检** | 换了 raw 的列或单位 |
| `calc.R` | 运算：只读 tidy + config | 换了模型或判据 |
| `out/tidy.csv` | 中间产物（可删可重建） | 不手改 |
| `result.txt` | 输出（ASCII，带 PASS/FAIL） | 不手改 |

## 单位自检为什么值得单独存在

raw 的那一列叫 `mbps`，实测语义是 **MiB/s**（`bytes / 1048576 / secs`）。这种"列名说谎"的错误
不会让程序崩，只会让结论大或小 1.048576 倍 —— 而且看起来很正常。

`standardize.py` 逐行验证 `declared ≈ derived`，容差**不是**拍一个数，而是把两处四舍五入传播开：

| 来源 | 影响 |
|---|---|
| `mbps` 保留两位小数 | ±0.005 MiB/s |
| `secs` 保留三位小数 | ±(bytes/MiB) × 0.0005 / s²；在 s=0.375 时约 ±0.91 MiB/s |

**这条容差本身就抓过一次错**：第一版按 `1e-6` 相对容差判，35/36 行报"单位不一致"；
第二版只加 ±0.005，仍有 23 行报错 —— 因为 `secs` 的三位小数在短耗时上放大得比 `mbps` 的两位还厉害。
把两项都传播之后才是 0。

## 阈值变更

`config.json` 里的三条阈值（`c8_over_c1=1.5`、`c16_over_c4=1.2`、`c64_over_c16=0.95`）
是 **2026-11-23 补写的**，不是这次测量之前定下的。所以：

> **它们只能用来演示管线，不能用来判定 e1 的结论。**
> e1 的真实结论看 `docs/reports/quant-report-*.md`（那一份的口径是测量前写的）。

下次真要判 e1，先把阈值写死在 `config.json` 里、再跑测量。
